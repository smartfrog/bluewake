# VITA-WW-11 — independent QEMU TCG reference for the scalar-VFP controls

2026-10-10 · [ticket](https://trello.com/c/Y5zsQQZK) · **positive discriminator: QEMU 32/32, fixture and oracles valid**

The 32 independent ARMv7 scalar-VFP control cases were executed on a second, independent reference
implementation — QEMU TCG, `vexpress-a9` / `cortex-a9` — and every observed bit pattern matched the
repository oracle table exactly, including all twelve cases that failed under Vita3K in VITA-WW-08 and
VITA-WW-09. By the accepted interpretation contract this confirms the fixture and the literal oracles;
the 08/09 control failures are therefore an execution-path observation on the Vita3K side (host is
aarch64, so the guest runs through dynarmic's arm64 backend), not a fixture or oracle defect. This is a
local, game-free, no-network diagnostic: no Vita3K process was started, no emulator or runtime was
rebuilt, and no gameplay result is claimed.

## Method

The harness reuses the fixture logic unmodified:

- `qemu_control.c` includes `arm_vectors.h` generated by the repository's own
  `arm_vectors.write_header` (the same generator the fixture uses), and links the unchanged
  `arm_vfp.c` and `arm_control.c`. Its control loop mirrors `arm_main.c`: read the initial FPSCR,
  request the case mode through `arm_fp_mode`, `VMSR` it, read it back, run
  `arm_vfp_operation`, read the post-operation FPSCR, restore the initial FPSCR through the
  fixture's own `arm_fp_restore`, and record raw requested/readback/after/actual/restored values.
- Two compile-time shims only: `-D__vita__=1` selects the real hard-float assembly branch of
  `arm_vfp.c` (that file contains no Vita API — the macro only gates the `VADD.F64`/`VMUL.F64`/
  `VCVT`/`VMRS`/`VMSR` sequences under test), and `-DNDEBUG` matches the fixture's CMake `Release`
  builds. The fixture code itself is untouched.
- `qemu_startup.S` sets SP into the 128 MiB vexpress RAM, enables CP10/CP11 access (`CPACR`) and the
  VFP unit (`FPEXC.EN`), then calls `main` and exits through semihosting (`SYS_EXIT`, reason
  `ADP_Stopped_ApplicationExit`).
- Output uses semihosting `SYS_WRITE0`; QEMU's native semihosting console emits it on stderr, which
  is where the runner reads the report from. Formatting writes go through a volatile byte buffer:
  `vexpress-a9` boots at EL3 with the MMU off, so unaligned accesses fault exactly as they would on
  real bare-metal hardware, and the harness must not rely on them.
- Determinism: no clocks, no entropy, no input. GCC's random temporary object name was removed by
  compiling each source to an explicitly named object before linking, so two independent runner
  invocations produce byte-identical ELFs and byte-identical reports.

Byte-exact build (per source, then link; from `scripts/vita/armv7/qemu_control.py`):

```sh
arm-none-eabi-gcc -std=c11 -O2 -ffp-contract=off -fno-fast-math -ffreestanding -mcpu=cortex-a9 \
  -mfpu=neon -mfloat-abi=hard -DNDEBUG -D__vita__=1 -Wall -Wextra -Werror -I<build> -c <source> -o <source>.o
arm-none-eabi-gcc -nostdlib -nostartfiles -static -Wl,-Ttext=0x60000000 -e _start <objects> -o qemu_control.elf
```

Byte-exact QEMU invocation (one machine run per runner invocation, bounded at 30 s; measured ~0.2 s
for the whole build+run):

```sh
qemu-system-aarch64 -M vexpress-a9 -cpu cortex-a9 -m 128M -display none -serial none -monitor none \
  -semihosting-config enable=on,target=native -kernel qemu_control.elf
```

`-M virt` rejects `cortex-a9` in this QEMU build (`cortex-a7`/`cortex-a15` only), so the dedicated
`vexpress-a9` machine with the Vita's CPU family is used.

Binary inspection proves the scalar instructions really execute: `arm_vfp_read` contains
`vmrs r0, fpscr`, `arm_vfp_write` contains `vmsr fpscr, r0`, `arm_vfp_add` contains
`vadd.f64 d2, d0, d1`, `arm_vfp_mul` contains `vmul.f64 d2, d0, d1`, and `arm_vfp_convert` contains
`vcvt.f32.f64 s4, d0` then `vcvt.f64.f32 d3, s4`. The runner refuses to launch QEMU when any of
these is missing from the built ELF. ELF attributes: `Tag_FP_arch: VFPv3`,
`Tag_ABI_VFP_args: VFP registers` (hard-float).

## The 71 runtime cases — deliberately not integrated

The runner skips the 71 pristine runtime cases. `fp_runtime.c` does not exercise ARM VFP
instructions: it drives the pinned PowerPC CPU core, the generated DolRecomp corpus chunks, the
composite direct-call dispatch and the guest-memory subsystem — the product runtime, plus host
`fenv` save/restore. Compiling that whole stack for bare-metal ARMv7 with semihosting I/O is not a
cheap extension of this harness, and it would measure recompiled PPC C arithmetic rather than the
ARM scalar-VFP semantics this discriminator is about. The runtime record is therefore an explicit
`RUNTIME skipped reason=not-integrated cases=71` line in the report, and the runner rejects a report
without it.

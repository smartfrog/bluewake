# Logo performance: the L1 poll-skip as a pinned build input

2026-10-18 · branch `task/perf-logo-60`, base `862b2ce1a7c6fec02480f83c28e6f5754f81cda0`.
Private POC package, one measured logo run. **No menu or gameplay claim, no 60 fps claim.**

## Result

| measurement | value |
| --- | --- |
| baseline (existing L1 trial #16, fast frames) | **17.4 fps** median (57.50 ms, n=178 of 296) |
| pre-L1 reference (trial #14, fast frames) | 8.5 fps median (117.60 ms) |
| this POC, fast frames | **19.7 fps** median (50.75 ms, n=239 of 296) |
| this POC, whole frame window | 5.96 fps over 49.689 s (297 presents) |
| this POC, 10 s windows | median 4.55 fps, p95 13.77, min 0.80 |
| this POC, best one-second bucket | 21 frames |
| target | 60 fps (floor 30) |

The fast-frame figure is the comparable logo number: it excludes the first-use shader/program stall and
the boot frames. The whole-window figure is dragged down by one **13.8 s** first-use shader compile
(frame 8) and by the boot; the 10 s windows begin at the first presented frame, so the first two
contain that stall. The best sustained one-second bucket is 21 frames, so even the fastest stretch is
about a third of 60 fps.

The named baseline package `perf-logo-baseline-20261018` already carries the L1 object; its payload
is byte-identical to this POC's payload. Its run `perf-logo-baseline-run-20261018-1` never wrote a
`ww05.request`, so the guest closed immediately and presented no frame. That run is a launch attempt,
not the 17 fps measurement. The 17.4 fps baseline above is the fast-frame median recorded by the
existing L1 trial #16, which used the same L1 object.

## Run

Two attempts, both disclosed:

1. `perf-logo-l1-pin-run-20261018-1` (setup): the request ran with strict audio and stopped at
   `DSP ROM task launch requires a DSP task backend` after 8 boot frames. It never reached the logo
   and is not used for the result.
2. `perf-logo-l1-pin-run-20261018-2` (measurement): the same request plus `ww05.audio` (deferred
   audio, the setting trial #16 used). Started 16:01:44, reached the title-logo stage, presented
   **297** frames and **306** retraces over **49.689 s**, then faulted at `TlogoE.arc` with
   `PC is 0x0` / `Unhandled SIGSEGV` and no `ww05.report` (`ww05.partial` 0 bytes). The process was
   stopped after the crash teardown did not exit. This is a crash result at the title-logo stage, not
   a menu, gameplay or clean-exit result.

Configuration: turn cap 4096, program cache ON, VI clock ON, idle-deadline advance ON, destination-
alpha admission ON, edge-observation admission ON, rejection capsule ON, RAM guard ON, pad input ON,
sentinel/observer OFF, reused object map, `audio=deferred`. Admission passed the 5,905,580,032-byte
floor; the scope ran at 99-124% CPU with a growing log until the fault.

## What the frames say

- **The post-present wait is the wall.** Median `retrace → present` is **3.16 ms**; median
  `present → next retrace` is **49.82 ms** (98% of the fast frame). The renderer side is not the
  limit at this scene.
- The frame window used **250,917 turns** (847.7 per frame) and advanced 2.451 B guest cycles
  (49.3 M cycles/s over the whole window). The idle leap fired **17** times: 14 jumps were bounded by
  an ARAM deadline at about 27,540-27,747 cycles, 2 by the VI deadline at 1.9 M and 2.7 M cycles, and
  1 by the decrementer at 5.1 M cycles. The idle-turn precondition was armed on only
  **3,393 of 257,995 turns (1.3%)**.
- This is the same shape trial #16 reported, with the builder's 4096-cycle cap instead of the sealed
  trial's 256-cycle cap: #16 logged `cap=256` and about 12,000 turns per frame at 57.50 ms; this run
  logs `cap=4096` and 848 turns per frame at 50.75 ms. The step from 17.4 to 19.7 fps is consistent
  with the cap change and run variance, not with a new lever.
- The 13.8 s frame is a first-use shader/program compile. The program cache is ON but cold; a warm
  run should remove that stall from the steady-state number.

## Next lever

The idle leap works when it fires: the long jumps each advanced 1.9-5.1 M guest cycles in one
turn. It fires almost never because 98.7% of turns fail the idle precondition and, when it does fire,
the nearest ARAM deadline usually clamps it to 27.5 k cycles. The next POC should **coalesce the
deferred-audio ARAM deadline and widen the idle-turn precondition so one idle turn covers a full
8.1 M-cycle VI period**. If the post-present wait collapses to one turn, the measured 3.16 ms
renderer phase is the floor and 60 fps becomes plausible; that is a hypothesis, not a result. A
warm-cache run is the cheap control that separates the first-use stall from the steady state.

## Limits

- One measurement run; it ended in the known title-stage fault and wrote no report. The frame series
  (`[frame-present]` / `[frame-timing]`) is the only source for the numbers.
- Vita3K timing is not physical Vita timing. Nothing here predicts the 444 MHz handheld.
- The public runtime pin is unchanged and the commit is unpublished. This is a private POC package,
  not an integration. Independent review is still required before integration.
- No menu, gameplay, audio, 30 fps or 60 fps claim.
